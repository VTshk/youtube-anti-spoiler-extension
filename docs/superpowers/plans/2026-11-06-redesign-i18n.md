## 1. Simplicity rules (owner rule, binding)

The code must be understandable by a developer working without an AI agent:
- direct `if`s and calls;
- no new layers, factories or event buses;
- functions small enough to see on one screen;
- names in plain words.

Do not handle impossible cases. Do not add `try/catch` that swallows errors. Real failures must still be handled:
storage read and write, fetch of a locale file, a missing DOM node on YouTube. Follow the existing code style of each
file. Comments only where the "why" is not obvious.

## 2. i18n framework

### 2.1 Files

- `_locales/en/messages.json`: every extension string, in Chrome's format:
  `{ "key": { "message": "...", "description": "where it is shown" } }`.
  - Key names are lowerCamelCase and grouped by prefix: `popup...`, `liveGuard...`, `comments...`, `skip...`,
    `manifest...`, `media...`.
  - **No placeholders (`$1`, `$NAME$`) anywhere.** Design strings so that none are needed. For example, the shortcut
    line is a label, "Shortcut:", plus a separate `<kbd>` element filled from `chrome.commands`.
- `manifest.json`:
  - `"default_locale": "en"`;
  - `name` = `__MSG_manifestName__`, which is "Anti-Spoiler for YouTube" in en;
  - `description` = `__MSG_manifestDescription__`, which is the current description text;
  - `action.default_title` = `__MSG_manifestName__`;
  - `commands.toggle-protection.description` = `__MSG_manifestToggleCommand__`.
  - No new permissions.
- `src/shared/i18n.js` is a new script. It is loaded in the popup, before `popup.js`, and in the isolated content
  scripts: in `manifest.json`, right after `src/shared/settings.js`. It goes on the existing `root.YouTubeAntiSpoiler`
  namespace, in the same style as `settings.js`. It holds only plain functions and one module variable, the override
  dictionary:
  - `SUPPORTED_LANGUAGES`: an ordered array of `{ code, nativeName }`, where `code` is the `_locales` folder name.
    - The order is English, Русский, Español, Português (Brasil), Deutsch, Français, 日本語, 한국어,
      Bahasa Indonesia, Türkçe.
    - For R1, include only `en`, because only `_locales/en` exists. Keep the list as one plainly visible array, so
      that R2 only adds lines.
  - `setMessages(messages)`: takes `{ key: text }` or `null`. Null means "no override, use the browser language".
  - `getText(key)`:
    1. the override text, if it has the key;
    2. otherwise `chrome.i18n.getMessage(key)`, which is the browser language with Chrome's own fallback to
       `default_locale`;
    3. if both are empty, the key itself, so a missing string is visible in testing and never blank.
  - `setText(element, key)`: sets `element.textContent = getText(key)` and `element.dataset.yasI18n = key`.
    `setLabel(element, key)` does the same for `aria-label` and `title`, with `data-yas-i18n-label`. Every translated
    element in the popup **and** in-page carries its key this way.
  - `applyTranslations(doc)`: re-runs `getText` for every `[data-yas-i18n]` and `[data-yas-i18n-label]` element in
    `doc`. Both the popup and `content.js` call it when the language changes. This is how already-open in-page panels
    switch language, and it needs nothing else.
  - `getHtmlLang(languageCode)`: the BCP 47 tag of the language actually shown. `pt_BR` becomes `pt-BR`.
    - For `"auto"`, take `chrome.i18n.getUILanguage()` and look for an exact `SUPPORTED_LANGUAGES` match, with `-`
      and `_` treated as equal, then a match on the base language. If neither matches, use `en`.
    - The popup sets `<html lang>` from it.
  - `fetchMessages(code)`, used **only by the popup**, which is an extension page and may fetch packaged files:
    `fetch(chrome.runtime.getURL("_locales/" + code + "/messages.json"))`, then convert to `{ key: message }`.
- **Where the chosen language lives:** in `chrome.storage.local`, NOT in the synced settings, under one key:
  `uiLanguage: { code, messages }`.
  - The key is absent when the language is "Browser language".
  - **Only the popup writes it.** Content scripts only read it, so no content script ever fetches extension files, and
    no `web_accessible_resources` are needed. This is the owner-approved "simpler way".
    - Why local: the language belongs to the device, like the browser language does.
    - A synced code without its messages would leave other devices with nothing to show.
  - Do not add `language` to `DEFAULT_SETTINGS` or `normalizeSettings`. `settings.js` does not change for this.

### 2.2 Content scripts

- **Protection never waits for translations.** This was Astra's review finding #1, and it is a blocker.
  - `content.js:1083–1116` applies protection synchronously before storage answers, and
    `tests/content.test.js:2996` tests this.
  - Keep that path exactly as it is. In-page controls are built at once with whatever `getText` returns at that
    moment, which is the browser language. When the stored language arrives, `applyTranslations(document)` updates
    their text.
  - Never reset guard state or rebuild a panel because of a language change.
  - Add a test: with a delayed `storage.local` read, protection classes are applied before the read resolves, and the
    text updates after it.
- **`content.js` is the only owner of language loading in content scripts.** This was finding #7.
  - At init, start `chrome.storage.local.get("uiLanguage")` next to the existing settings read, without awaiting it
    before protection.
  - On result, call `setMessages(uiLanguage ? uiLanguage.messages : null)`, then `applyTranslations(document)`, then
    write the media title attribute (see the bridge item below).
  - In its `storage.onChanged` listener, also handle `areaName === "local" && changes.uiLanguage`, with the same steps.
    The current listener filters keys by `CLASS_BY_SETTING` (`content.js:1154`) and areas by `sync`. Add a separate,
    explicit branch; do not add a CSS class for the language.
  - `live-start-controller.js` and `skip-buttons.js` do not load or listen to anything. They just call
    `setText` / `setLabel` / `getText` when they build or update elements.
- **No translated text is cached at module load.** This was finding #8.
  - `skip-buttons.js:16–23` builds `SKIP_STEPS` at script evaluation. Store a message key per step, such as
    `labelKey`, and resolve it in `createSkipButton()` through `setLabel`.
  - The live guard panel's changing texts ("Checking…", "can't be rewound", the ad note) must also go through `setText`
    with their key each time they change, so `applyTranslations` re-applies the current state's text and not an old
    one.
- **Do NOT translate strings that match YouTube's own DOM or labels.** For example, `"Up next"`, `"Key moments"`,
  `"Most replayed"` and `"Show less"` in `content.js` selectors and comments identify YouTube elements; they are not
  our UI. When unsure, look at how the string is used.
- **Media title for the MAIN world** (finding #9):
  - `live-player-bridge.js` cannot use `chrome.i18n`.
  - `content.js` writes `getText("mediaHiddenTitle")` into `document.documentElement.dataset.yasMediaTitle`
    (`data-yas-media-title`) at init and after each language change.
  - The bridge reads that attribute wherever it uses `HIDDEN_MEDIA_TITLE` today, falling back to `"YouTube video"`
    when the attribute is absent.
  - Add `data-yas-media-title` to the bridge's existing `<html>` observer `attributeFilter`
    (`live-player-bridge.js:631–642`), so the masked metadata is reapplied when only the language changes.
  - Test: with the classes unchanged and no new YouTube metadata assignment, changing only the attribute updates
    `mediaSession.metadata.title`.
- `src/background/background.js` has no visible strings. Do not change it unless you find one.

### 3.1a Popup language flow (Astra findings #2, #3, #5)

The language is NOT part of the settings save queue, because it is a separate `storage.local` key.

- **Startup order:**
  1. Read the settings and `storage.local.uiLanguage`. The two reads are independent.
  2. Call `setMessages(uiLanguage ? uiLanguage.messages : null)`.
  3. Set `<html lang>` = `getHtmlLang(uiLanguage ? uiLanguage.code : "auto")`.
  4. Call `applyTranslations(document)`.
  5. Render the dynamic parts: status, notes, the skip dependency note, the shortcut, and the select value.
  - If the settings read fails, still do steps 2–4, then show the localized load error and keep read-only mode, as
    today.
  - If the `uiLanguage` read fails, use `null` (browser language) and continue.
- **Select change, where the latest choice wins:**
  - Keep a counter `languageRequest` and increment it on each change.
  - For `"auto"`: `storage.local.remove("uiLanguage")`.
  - For a code: `messages = await fetchMessages(code)`, then `storage.local.set({ uiLanguage: { code, messages } })`.
  - After each await, if the counter has moved on, stop and do nothing more. A newer choice is in charge.
  - On success: `setMessages`, `<html lang>`, `applyTranslations`, re-render.
  - On a failed fetch or write: set the select back to the last confirmed language and show
    "Could not change the language" (a new key) in the status line. Keep the shown language as it was.
- **External change** (another popup window): `storage.onChanged` with `areaName === "local"` and
  `changes.uiLanguage` runs the same steps as a successful change, using `newValue` (absent means browser language).
- Do not route this through the settings `saveQueue`. The two are independent, and keeping them apart is simpler.
