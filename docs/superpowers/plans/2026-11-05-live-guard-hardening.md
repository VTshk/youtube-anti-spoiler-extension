## Цель и главный инвариант

Защита эфира существует ради одного: **пользователь не должен увидеть или услышать текущий момент эфира, пока сам явно
не выбрал «Continue live»**. Отсюда правило для каждого спорного места: при неопределённости — оставаться под защитой
(блюр + mute + пауза), а не снимать её. Снимать защиту можно только по:
- явному выбору пользователя («Continue live», или «Start from beginning» после *подтверждённой* перемотки к началу);
- подтверждённому признаку «это не эфир» для **того же** videoId (VOD, запись прошедшего эфира);
- выключению настройки / защиты;
- реальному уходу с этого видео (другое видео, плеер закрыт).

### B2. «Start from beginning» снимает защиту до перемотки; без DVR — запускает live
Место: `live-start-controller.js` `startFromBeginning` (~872-888), `dismissGuard`.
Нужно:
1. После нажатия — защита (блюр + mute + пауза) остаётся, пока перемотка не подтверждена: `video.currentTime` оказался
   рядом с началом DVR (в пределах нескольких секунд от `seekable.start(0)`), либо мост прислал успешный
   `LIVE_START_SEEK_RESULT_EVENT` с тем же `requestId`. Только после этого — снять блюр, вернуть звук, `play`.
2. Перемотка не подтвердилась за разумное время (2–3 с) — защита остаётся, оверлей показывает строку
   «Couldn't jump to the beginning.» и обе кнопки снова доступны. Не помечать видео как выбранное.
3. DVR нет (`seekable.length === 0` или окно перемотки нулевое) — кнопку «Start from beginning» не показывать (или
   показать неактивной), текст: «This stream can't be rewound. Continue live or leave the page.» Остаётся только
   «Continue live» — это явное согласие.
4. Тест `tests/content.test.js` «live guard start from beginning fails open when DVR is unavailable» (~1753) закрепляет
   ошибочное поведение — заменить тестом на новое поведение.

### B3. Решение запоминается до перезагрузки вкладки
Место: `attemptedVideoIds` (~438, ~848), `getLiveStartTarget`.
Нужно: выбор действует, пока пользователь остаётся на этом видео (включая повторные SPA-события и перерисовки той же
страницы — оверлей не должен появляться снова). Как только плеер переключился на **другое** видео, все прежние решения
сбрасываются: вернувшись на прежний эфир, пользователь снова видит выбор. Уход на главную с мини-плеером этого же видео
(B6) решение **не** сбрасывает.

### B4. Реклама перед эфиром
Место: `isLikelyLivePlayback` (~225-240), `showGuard`, обработчики кнопок.
Признак рекламы: у `#movie_player` класс `ad-showing` (или `ad-interrupting`).
Нужно: пока идёт реклама — защита (блюр + mute) держится, но реклама не ставится на паузу (иначе она не закончится);
кнопки скрыты, текст оверлея «Waiting for the ad to finish…». Никакое действие во время рекламы не считается выбором и не
помечает видео. Когда реклама закончилась — обычный guard для самого эфира (пауза, кнопки).

### B5. «Неизвестно» превращается в «точно не эфир»
Место: `live-player-bridge.js` `getLiveState` (~182-202); в контроллере `pageWorldSaysCurrentVideoIsNotLive` и снятие
раннего щита (~1066-1080).
Нужно: мост различает три состояния — `isLive: true`, `isLive: false` (есть явный признак не-эфира для этого видео:
поле live в `videoData` равно false **и** есть player response того же videoId без признаков live, либо явный
`isLiveContent`/`isLive` false), `isLive: null` (данных ещё нет). Контроллер снимает ранний щит только по `false`.

### B6. Мини-плеер снимает защиту
Место: `getLiveStartVideoId` (~60-85), `sync` → `cancel`.
Нужно: если guard активен (выбор не сделан) и пользователь ушёл со страницы просмотра, а тот же плеер продолжает жить
(мини-плеер), защита остаётся: пауза, mute, блюр (CSS уже действует на `#movie_player video`). Оверлей в маленьком
мини-плеере можно не показывать; при возврате на страницу видео guard продолжается с кнопками. Если плеер закрыт
(видео пропало) или в нём другое видео — `cancel`. ID видео в плеере — из ответа моста (`LIVE_STATE_RESULT_EVENT`
содержит `videoId`) или иного уже имеющегося источника; новых каналов связи не вводить без необходимости.

### B7. Новый `<video>` играет со звуком до следующего опроса
Место: `bindPauseLock`, heartbeat (~1040-1048).
Нужно: пока guard активен (и в фазе раннего щита), любое `play`/`playing`/`loadeddata` любого `<video>` в документе
сразу приводит к паузе (кроме рекламы — B4) и mute. Медиасобытия не всплывают — слушать на `document` в фазе захвата
(`addEventListener(..., true)`) и снимать слушатели при снятии guard.

### B8. Запись прошедшего эфира принимается за эфир
Место: `isLikelyLivePlayback` (~225-240), ветка `activeGuard.guarded` в тике.
Нужно: явный признак «не эфир / эфир закончился» для того же videoId (мост `isLive:false`, `documentSaysVideoIsNotLive`,
`endDate`) имеет приоритет над слабыми признаками (`duration=NaN` + класс `ytp-live` или наличие чата). Если guard уже
показан, а затем пришёл явный признак «не эфир» для этого видео — снять guard и продолжить воспроизведение (видео было
поставлено на паузу нами). Тесты ~845 и ~880 («shows for the active YouTube player live class», «...live chat frame»)
дополнить случаем с явным not-live признаком.

### B9. Мост смешивает признаки разных видео
Место: `live-player-bridge.js` `getLiveState` (~182-202).
Нужно: объединять признаки только из источников с тем же videoId, что и текущее видео плеера (`videoData.video_id`);

### B10. Полноэкранный режим скрывает оверлей

Нужно: когда `document.fullscreenElement` есть, оверлей монтируется внутрь него и позиционируется по нему; при выходе из

### B12. `/@channel/live`, `/channel/<id>/live`, `/c/<name>/live`

Нужно: на этих путях определять videoId текущего плеера (мост или `link[rel="canonical"]` с `watch?v=`), чтобы

## Решения после критики плана (Astra, 2026-11-05) — имеют приоритет над текстом пунктов выше

**R1 (B2) — что значит «перемотка подтверждена».** Ждать события `seeked` на защищаемом `<video>`, затем проверить
`!video.seeking` и `|video.currentTime − цель| ≤ 5 с`, затем дождаться следующего отрисованного кадра
(`video.requestVideoFrameCallback`, если есть; иначе один `requestAnimationFrame`) — и только тогда снять блюр, вернуть
звук и запустить. Ответ моста `LIVE_START_SEEK_RESULT_EVENT` сам по себе не подтверждение. Ожидающая перемотка
отменяется (без снятия защиты) при смене видео, начале рекламы, выключении защиты и новом нажатии; поздний ответ/событие
от отменённой перемотки игнорируется. Таймаут 3 с — защита остаётся, строка «Couldn't jump to the beginning.»,
кнопки снова доступны. Тесты: «currentTime уже у цели, но seeking=true / кадра ещё нет → защита держится»;
«seeked пришёл после смены видео → игнор».

**R2 (инвариант, P2) — 10-секундный таймаут больше не снимает защиту.** Если за `LIVE_START_TIMEOUT_MS` статус так и не
стал известен (`isLive` не true и не false), а `<video>` есть — показать оверлей с текстом «Couldn't tell whether this
is a live stream.» и двумя кнопками: «Start from beginning» (как B2) и «Play» (продолжить с текущего места, без перемотки
к live-краю). Это явное согласие. Тест на >10 с без сигнала.

**R3 (B8, P3) — показанный оверлей сам не исчезает.** Как только оверлей с кнопками показан, снимает его только выбор
пользователя, выключение защиты или уход с видео (R4). Пришедший после этого признак «эфир закончился / не эфир» guard
не снимает и сам ничего не запускает (иначе раскроется финал). Ложную классификацию B8 исправлять *до* показа: слабые
признаки (`duration=NaN` + класс `ytp-live` или наличие чата) не дают показать guard, если для того же videoId уже есть
явный признак «не эфир» (`endDate`, `isLiveBroadcast=false`, мост `isLive:false`). Пока явных признаков нет, слабые
признаки дают только ранний щит (блюр + mute), не оверлей, в течение `LIVE_START_NOT_LIVE_GRACE_MS`; если за это время
пришёл явный «не эфир» — щит снимается (раньше показа оверлея это допустимо).

**R4 (B3, B6, P4, P8) — когда guard отменяется.** Отмена — только при: выключении настройки/защиты; плеер показывает
**другое** videoId (по URL страницы просмотра или по ответу моста); плеер закрыт — `#movie_player` отсутствует в DOM или
мост не возвращает videoId **3 с подряд**. Временное отсутствие `<video>` (YouTube пересоздаёт элемент) отменой не
считается: защита и перехват событий (R6) остаются. Решения пользователя (`attemptedVideoIds`) сбрасываются только при
переходе плеера к другому videoId. В мини-плеере оверлей показывается поверх мини-плеера в компактном виде: если ширина
плеера < 480 px, текст-пояснение скрывается, остаются заголовок и кнопки.

**R5 (B4, P5, P6) — реклама.** Признак: класс `ad-showing` или `ad-interrupting` у `#movie_player`. На время рекламы:
блюр + mute остаются, но паузы нет — если пауза стоит потому, что её поставил guard, снять pause-lock и вызвать `play`
(рекламу, остановленную самим пользователем, не запускать). Вместо панели с кнопками — небольшая подпись
«Ad — the choice will appear after it» с `pointer-events: none`, не перекрывающая кнопку «Skip ad». Выбор во время
рекламы невозможен и ничего не помечает. Реклама закончилась — сразу пауза и обычный guard с кнопками.

**R6 (B7, P7) — перехват запуска.** Слушатели `play`/`playing`/`loadeddata` на `document` в фазе захвата, но реагировать
только на `<video>` внутри `#movie_player` (защищаемого плеера); превью при наведении и другие плееры не трогать.
Один сохранённый mute-state, как сейчас. Снимать слушатели при снятии guard.

**R7 (B2, P9) — «DVR не готов» ≠ «DVR нет».** Пока `seekable.length === 0`, кнопка «Start from beginning» видна, но
неактивна, подпись «Checking whether the stream can be rewound…». Проверять на каждом тике и обновлять существующие
элементы оверлея (не пересоздавать). «This stream can't be rewound…» показывать, только если `video.readyState ≥ 1` и
перемотки нет дольше 3 с. Тест empty → nonempty.

**R8 (B5, B9, P10, вопросы) — контракт live-state моста.**
Порядок источника ID: `videoData.video_id` → `getPlayerResponse().videoDetails.videoId` →
`ytInitialPlayerResponse.videoDetails.videoId`. Учитываются только источники с тем же ID, источники с другим ID
игнорируются, источник без ID — тоже. Значение `isLive`:
| Признаки (только совпадающие по ID источники) | isLive |
|---|---|
| хоть один говорит «идёт сейчас» (`videoData.isLive`, `videoDetails.isLive`, `liveBroadcastDetails.isLiveNow` = true) | `true` (защитный приоритет) |
| никто не говорит «идёт», и есть явный признак «не идёт»: `liveBroadcastDetails.isLiveNow === false`, или есть `liveBroadcastDetails.endTimestamp`, или `videoDetails.isLiveContent === false` | `false` |
| иначе | `null` |
Приёмник (`parseLiveStateResult` или аналог) должен принимать `null`. Снимок устаревает при смене videoId.

**R9 (B12) — ID на `/@x/live`, `/channel/<id>/live`, `/c/<x>/live`, `/user/<x>/live`.** Брать атрибут `video-id`
видимого `ytd-watch-flexy` (`ytd-watch-flexy:not([hidden])`), запасной вариант — `link[rel="canonical"]` с `watch?v=`.
Новых каналов связи не вводить.

**R10 (B14, P11) — чат.** После быстрых повторов продолжать проверку раз в 1 с, пока условия чат-гарда выполняются, —
в том числе после успешного монтажа: если оверлей пропал (YouTube пересоздал чат), смонтировать снова. Одна редкая
проверка, без MutationObserver.

**R11 (P12) — приёмка.** Исполнитель закрывает клетки unit-тестами; живую проверку в браузере делает главная сессия.
| Сценарий | unit (исполнитель) | живьём (главная сессия) |
|---|---|---|
| live, DVR есть: «Start from beginning» — защита до кадра у начала | да | да |
| live, DVR грузится → появился; DVR нет | да | если найдётся эфир без DVR |
| реклама → live; поздний класс `ad-showing` | да | если попадётся реклама |
| VOD с повтором чата (с `endDate`) — без guard | да | да (запись эфира) |
| live → эфир закончился при показанном оверлее — оверлей остаётся | да | нет (не вызвать) |
| мини-плеер: уход/возврат/закрытие/временная замена `<video>` | да | да |
| полноэкранный режим до и после guard | да | да |
| смена видео / выключение защиты во время ожидающей перемотки | да | нет |
| статус неизвестен >10 с — оверлей «Couldn't tell…» | да | нет |

## R12 — живая проверка 2026-11-05: эфир на паузе никогда не узнаёт окно перемотки

Факт (живой YouTube, Chromium 1248, эфир `W3rwZZzyOok`): guard ставит эфир на паузу до старта воспроизведения;
через 10 с и 30 с — `video.readyState=0`, `seekable` пуст, `player.getProgressState()` = `{seekableStart:0,
seekableEnd:0, duration:0}`, `player.seekTo(0)` ничего не загружает. Кнопка «Start from beginning» навсегда остаётся
в «Checking…», доступно только «Continue live». (Старый код это скрывал: «с начала» при пустом окне просто запускал live.)
Ещё факт: при показанном guard `video.muted` иногда `false` — YouTube возвращает звук через свой API.

Нужно:
1. **Фаза загрузки.** Пока guard активен и окно перемотки неизвестно (`seekable` пуст или `readyState < 1`), видео
   **играет** невидимым и без звука, чтобы плеер загрузил поток; как только окно перемотки известно — пауза, кнопки.
   Блокировка запуска (R6) в эту фазу не ставит паузу. Пауза, поставленная самим пользователем, — не наша забота
   (до выбора пользователь управлять плеером не может: оверлей его закрывает).
2. **Пиксели под guard не видны вовсе:** под классом live-защиты у `<video>` `opacity: 0` (блюр можно оставить или
   убрать — проще убрать; тест CSS поправить).
3. **Звук держится:** в обработчик захвата R6 добавить `volumechange` — если щит стоит, а `<video>` внутри
   `#movie_player` размучен не нами, снова заглушить (сохранённое исходное состояние звука не перезаписывать).
4. Если за `LIVE_START_TIMEOUT_MS` фазы загрузки окно так и не появилось — R7 «can't be rewound» (как сейчас).
5. Тесты: «guard на паузе с пустым seekable запускает видео без звука и невидимым; появился seekable — пауза и активная
  кнопка»; «YouTube размутил видео под guard — снова заглушено».

## R13 — ревью реализации (Astra, 2026-11-05): обязательные исправления

Все пять находок подтверждены Node-пробами на настоящих модулях; полный текст — в сообщении ревьюера, суть:
- **I1.** Ожидающая перемотка должна отменяться при смене защищаемого `<video>`; перед подтверждением проверять, что
  `seek.video` — всё ещё текущее защищаемое видео. Тест: Start → seeked старого → подмена `<video>` → rVFC/500 мс
  старого → guard держится, новое видео не запущено.
- **I2.** Перед подтверждением перемотки проверять рекламу: если `ad-showing`/`ad-interrupting` — отменить перемотку и
  перейти в рекламную фазу, выбор не записывать. Тест: класс рекламы появился после seeked, callback кадра — до heartbeat.
- **I3.** Чат: если чат-гард снят по «не эфир», а потом live-контроллер для того же видео начал ждать выбора — чат снова
  защищён. Тест false → true для одного ID.
- **I4.** Пока guard активен, `<video>` искать только внутри `#movie_player`; если его там временно нет — `null`
  (guard остаётся), без глобального `querySelector("video")`. Одинаково для heartbeat, кнопок и перехвата.
- **I5.** Мост: `liveStreamability` убрать из признаков «идёт сейчас» (таблица R8 — контракт). Тесты: response с
  `liveStreamability` + `isLiveNow:false` → `false`; без явных true/false → `null`.

Решения главной сессии по вопросам ревьюера:
- **Q1 (повторное открытие после закрытия мини-плеера).** Если пользователь не на странице просмотра и защищаемое видео
  остановлено или отсутствует (мини-плеер закрыт), решения (`attemptedVideoIds`, `lastPlayerVideoId`) сбрасываются:
  следующее открытие того же эфира снова спросит. Если видео продолжает играть в мини-плеере — решение держится.
- **Q2 (пауза пользователя).** Возобновлять только то, что остановили мы: перед нашей паузой запоминать, играло ли видео
  (`pausedByGuard`), и при входе в рекламную фазу / выходе из фазы загрузки R12 запускать только при `pausedByGuard`.

## Чего не делать

- Не вводить новых слоёв, фабрик, шин событий и конфигов поведения. Код должен читаться сверху вниз (правило проекта:
  человек без агента должен понять, что делает функция, и где её править).
- Не трогать селекторы и логику скрытия времени/превью/названий из порции 1.
- Не менять тексты, которые не названы в плане. Новые строки — по-английски, как остальной интерфейс.
- Не добавлять разрешений в manifest.
- Невозможные сценарии не обрабатывать (не проверять то, что гарантирует код выше).
