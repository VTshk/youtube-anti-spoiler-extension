## Высокая

### C1. VOD с повтором чата (или после live) навсегда попадает под live-guard; «Continue live» перематывает в конец записи
- **Файл:** `src/content/live-start-controller.js:225-240` (`isLikelyLivePlayback`), `:30-34` (`LIVE_CHAT_SELECTORS`), `:1058-1065` (ветка `guarded`), `:858-861` + `:326-339` (`seekVideoToLiveEdge`).
- **Что не так:** третья ветка `isLikelyLivePlayback` срабатывает при `!Number.isFinite(video.duration)` и (`#movie_player.ytp-live` ИЛИ любой элемент чата). Ни положительный not-live из page-world (`isLive:false` для этого id), ни `endDate` здесь не проверяются. При этом `duration` равен `NaN` у любого видео, пока не загружены метаданные (новый `src`/MediaSource). Селекторы чата совпадают и с повтором: `ytd-live-chat-frame` есть у записей трансляций, а `iframe[src*="/live_chat"]` совпадает с `/live_chat_replay`. Достаточно одного тика (раз в 100 мс), и guard ставится. Дальше ветка `guarded` (`:1058`) не снимает его даже при явном not-live. Если нажать «Continue live», `seekVideoToLiveEdge` выставит `currentTime = seekable.end` = длительность записи, и пользователь увидит финал матча.
- **Сценарий:** смотреть запись матча (законченная трансляция с повтором чата), в рекомендациях кликнуть запись другого матча того же канала (SPA, чат-фрейм остаётся в DOM). Пока новый `src` грузится (`duration = NaN`), тик видит чат → пауза, блюр, оверлей «This live stream was paused…». Если нажать «Continue live», видео прыгнет в конец. Второй путь: со стрима L, где выбран «Continue live», перейти на запись V. Пока у плеера висит `ytp-live`, а `duration = NaN`, получится тот же результат.
- **Тесты закрепляют:** `tests/content.test.js:845`, `:880` проверяют только эвристику без not-live; `:967` проверяет устаревший `ytp-live` только при конечной `duration`, случай `NaN` не покрыт. `:1149` закрепляет «не снимать guard».
- **Простое исправление:** в `isLikelyLivePlayback` эвристику (третью ветку) включать только если нет положительного not-live: `!pageWorldSaysCurrentVideoIsNotLive(...) && !documentSaysVideoIsNotLive(...)`. В ветке `guarded` в `runTick` снимать guard (`cancel(doc,false)`), если `isClearlyNotLivePlayback(...)`. В `dismissGuard` для `"live"` вызывать `seekVideoToLiveEdge` только когда page-world подтвердил `isLive === true`.
- **Статус:** подтверждено по коду (логика). Насколько часто `NaN` и чат совпадают по времени на живом YouTube — гипотеза.

### C2. «Start from beginning» снимает блюр до того, как перемотка завершилась: кадр live-момента виден открыто
- **Файл:** `src/content/live-start-controller.js:872-888` (`startFromBeginning`), `:855-856` (`removeLiveStartObscuring` внутри `dismissGuard`).
- **Что не так:** перемотка запрашивается асинхронно (`seekTo` в мосту + `video.currentTime = start`), а оверлей и класс блюра снимаются синхронно в том же обработчике клика. Пока DVR-сегмент грузится, `<video>` показывает последний декодированный кадр, а это текущий live-момент, на котором guard поставил паузу: счёт, табло. Результат перемотки (`LIVE_START_SEEK_RESULT_EVENT`) мост отправляет, но контент-скрипт его нигде не слушает (grep: только экспорт констант). Если перемотка не удалась, поток идёт с live-края без блюра и со звуком.
- **Сценарий:** открыть идущую трансляцию матча, дождаться оверлея, нажать «Start from beginning». От 0,5 до 2 с, пока идёт перемотка, виден чёткий кадр текущего момента.
- **Простое исправление:** для `"start"` не снимать `LIVE_START_OBSCURED_CLASS` сразу. Снимать по событию `seeked` у `video` (одноразовый слушатель) или по результату моста с `success:true`, с таймаутом-предохранителем (например, 3 с). При `success:false` оставить блюр и вернуть оверлей.
- **Статус:** подтверждено по коду. То, что во время перемотки на экране остаётся последний кадр, — стандартное поведение `<video>`.

### C3. Возврат к той же трансляции в той же вкладке — guard не ставится никогда (attemptedVideoIds живёт до перезагрузки)
- **Файл:** `src/content/live-start-controller.js:438`, `:847-849`, `:88-101` (`getLiveStartTarget`: `!attempted.has(videoId)`).
- **Что не так:** после любой кнопки id попадает в `attemptedVideoIds` навсегда, на всё время жизни вкладки. Live-стримы YouTube при повторном открытии стартуют с live-края.
- **Сценарий:** открыть трансляцию L, нажать «Start from beginning», смотреть. Кликнуть рекомендацию или вкладку канала, затем нажать «Назад» (или открыть L из истории). L откроется на live-крае без блюра, звука и оверлея — текущий счёт виден.
- **Простое исправление:** хранить `lastWatchVideoId`. В `sync`, когда приходит другой ненулевой videoId (переход на другое watch-видео), делать `attemptedVideoIds.clear()`. Переход на главную с мини-плеером id не меняет, поэтому лишнего повторного guard не будет.
- **Статус:** подтверждено по коду. Старт live с live-края при возврате — гипотеза о поведении YouTube (типично для live без сохранённой позиции).

### C4. Pre-roll-реклама на трансляции: выбор пользователя применяется к рекламе, после неё идёт live без защиты
- **Файл:** `src/content/live-start-controller.js:1025-1049` (guard на любом `<video>`), `:872-888`, `:839-866`.
- **Что не так:** реклама играет в том же `video.html5-main-video`, а `getVideoData()` возвращает id и `isLive` основного видео. Guard встаёт во время рекламы: `getEarliestSeekableStart` берёт seekable рекламы (0), `video.currentTime = 0` перематывает рекламу, `seekTo` моста во время рекламы плеер игнорирует. Затем `dismissGuard` помечает видео как attempted и снимает блюр и mute. Когда реклама кончится, основной поток стартует с live-края открыто. Состояние `#movie_player.ad-showing` нигде не проверяется (grep: `ad-showing` в коде нет).
- **Сценарий:** открыть трансляцию с pre-roll, на оверлее нажать «Start from beginning» во время рекламы. После рекламы live-момент виден со звуком.
- **Простое исправление:** пока у `#movie_player` есть класс `ad-showing`, кнопки только запоминают выбор (`activeGuard.pendingAction = "start"|"live"`), а guard остаётся. На тике, когда `ad-showing` пропал, выполнить запомненное действие.
- **Статус:** гипотеза (поведение плеера во время рекламы). Отсутствие обработки рекламы подтверждено по коду.

### C5. URL вида `/@channel/live` и `/channel/UC…/live` не считаются watch-страницей: нет ни live-guard, ни чат-гарда

- **Что не так:** для `/@Channel/live` функция возвращает `null`, поэтому `sync` → `cancel` и чат-гард тоже снимается.

- **Простое исправление:** если путь заканчивается на `/live`, брать id из `ytd-watch-flexy[video-id]` или `meta[itemprop="videoId"]` (из документа, без новых слоёв).

### C6. Уход со страницы стрима (мини-плеер) снимает блюр с поставленного на паузу live-кадра
- **Файл:** `src/content/live-start-controller.js:1108-1110` (`!shouldAttempt` → `cancel`), `:855-856`.
- **Что не так:** на главной или в поиске `videoId = null`, поэтому `cancel` снимает класс блюра, оверлей и mute. Видео остаётся на паузе на live-кадре, а YouTube показывает его в мини-плеере уже без блюра. Нажатие play в мини-плеере запускает live без выбора.
- **Сценарий:** открыть трансляцию (оверлей на месте), нажать на логотип YouTube или «Назад» к ленте. В мини-плеере виден чёткий кадр текущего момента.
- **Простое исправление:** если guard был показан (`activeGuard.guarded`) и уход идёт не на другое watch-видео, не делать `cancel`, а оставить блюр и паузу, пока мини-плеер существует (например, пока `#movie_player` в DOM и `ytd-miniplayer` активен). Минимальный вариант — при уходе с непрошедшим guard ставить `video.pause()` и оставлять класс блюра до следующего watch-перехода.
- **Статус:** подтверждено по коду. Показ мини-плеера для видео на паузе — гипотеза о поведении YouTube.

### C8. В полноэкранном режиме оверлей с кнопками невидим: плеер заблюрен и на паузе без возможности выбрать
- **Файл:** `src/content/live-start-controller.js:520-529` (хост — `doc.body`), `:632`.
- **Что не так:** в fullscreen отрисовывается только поддерево `document.fullscreenElement` (у YouTube это контейнер плеера или приложения, не `body`). Оверлей — прямой потомок `body`, поэтому его не видно, и z-index это не исправит. `fullscreenchange` только пересчитывает координаты.
- **Сценарий:** смотреть обычное видео в fullscreen, автоплей переходит на live (или нажать F, пока стоит оверлей). Видно чёрно-размытое окно без кнопок, выход только через Esc.
- **Простое исправление:** в обработчике `fullscreenchange` и при монтировании: `(doc.fullscreenElement || doc.body).appendChild(overlay)`. В fullscreen задать оверлею `position: fixed; inset: 0`.
- **Статус:** подтверждено по коду и по семантике Fullscreen API.

### C9. Мост смешивает live-признаки разных видео: устаревший `ytInitialPlayerResponse` + id текущего `videoData`
- **Файл:** `src/content/live-player-bridge.js:165-181`, `:183-204`.

Если `getPlayerResponse()` вернул `null` или бросил исключение, берётся `ytInitialPlayerResponse` от первой загрузки страницы (она могла быть трансляцией). Тогда наружу уходит `{videoId: <текущее обычное видео>, isLive: true}`, и срабатывает C1-подобная блокировка, где «Continue live» ведёт в конец записи.
- **Сценарий:** полная загрузка страницы трансляции L, затем SPA-переход на запись R. В момент, когда плеер ещё не отдаёт response R, guard встаёт на R.
- **Простое исправление:** учитывать `playerResponseLive` только если `getPlayerResponseVideoId(playerResponse) === videoDataVideoId` (или `videoData` пуст). Фолбэк на `ytInitialPlayerResponse` убрать или проверять его id так же.
- **Статус:** подтверждено по коду (дефект сопоставления). Момент `null` от `getPlayerResponse` — гипотеза.

### C10. Чат-гард на VOD после SPA-перехода опирается только на микроразметку DOM — повтор чата остаётся заблюренным
- **Файл:** `src/content/content.js:498-500`, `src/content/live-start-controller.js:204-223`.
- **Что не так:** `documentSaysVideoIsNotLive` требует `meta[itemprop="videoId"]` текущего видео. Блок `meta itemprop` приходит в серверном HTML, и при SPA-навигации он, по всей видимости, не обновляется. Page-world состояние (`isLive:false`), которое уже есть у live-контроллера, чат-гард не использует. Итог: на записи, открытой SPA-переходом, повтор чата закрыт «Comments hidden». Это противоречит README («Recordings of finished streams are not affected») и исправлению из 372fee4.
- **Сценарий:** с главной кликнуть запись прошедшей трансляции. Повтор чата заблюрен.
- **Простое исправление:** контроллер при положительном not-live (`pageWorldSaysCurrentVideoIsNotLive` или `isClearlyNotLivePlayback`) кладёт id в `notLiveVideoIds` и экспортирует `isKnownNotLive(videoId)`. `syncChatGuard` проверяет его вместе с `documentSaysNotLive` и вызывается повторно с тика, когда статус стал известен.
- **Статус:** гипотеза (что микроразметка устаревает при SPA). То, что чат-гард не видит page-world, подтверждено по коду.

### C11. Инлайн-превью при наведении на карточку (лента, поиск) не закрыто: на live-карточке виден текущий момент

- **Статус:** отсутствие селектора подтверждено по коду; имена элементов YouTube — гипотеза (живьём не проверено).

### C12. Live-блюр накрывает только `<video>`; заглушка-миниатюра плеера и фон под 82%-оверлеем остаются читаемыми

### C13. Встроенные плееры (embed) не защищены: нет `all_frames`, путь `/embed/` не распознаётся live-guard

- **Статус:** подтверждено по коду и манифесту. README явно embed не обещает, но поведение стоит зафиксировать.

### C14. `yt-navigate-start` не «вооружает» щит заранее, как утверждает комментарий
- **Файл:** `src/content/content.js:589-601`; `live-start-controller.js:1103-1105` (videoId берётся из `location.href`).
- **Что не так:** на `yt-navigate-start` URL ещё старый, поэтому `sync` работает с предыдущим видео (или с главной, где `cancel`). Целевой URL лежит в `event.detail.url`, но изолированный мир не видит объектный `detail` из MAIN-мира. Фактически щит ставится на `pushState`/`yt-navigate-finish`. Если плеер начал рисовать новый стрим раньше `pushState`, первые кадры и звук проходят без блюра.
- **Сценарий:** с главной кликнуть карточку идущей трансляции. Короткое окно без блюра и mute.
- **Простое исправление:** в мосту (MAIN) слушать `yt-navigate-start` и отправлять `REFRESH_EVENT`-подобное событие с `JSON.stringify({url: e.detail.url})`. В контенте по нему сразу ставить `LIVE_START_OBSCURED_CLASS` для целевого `/watch` или `/live`.
- **Статус:** неверный комментарий подтверждён по коду. Наличие видимого окна — гипотеза.

### C16. При выключенной «Hide progress bar» подсказка таймлайна показывает кадры раскадровки из будущего и названия глав

- **Что не так:** обязательное скрытие времени не мешает навести курсор на таймлайн и увидеть кадр, например, табло на 85-й минуте.
- **Простое исправление:** под `yas-hide-time` скрывать и `.ytp-tooltip-bg`, `.ytp-tooltip-title` (или блюрить их).
- **Статус:** подтверждено по коду; спорно как продуктовое решение — вынести владельцу.

### C17. Системные медиаконтролы (Chrome Global Media Controls, Windows) показывают позицию и длительность
- **Файл:** нет кода (`navigator.mediaSession` нигде не трогается — grep).
- **Что не так:** Chrome передаёт позицию и длительность активного видео в меню медиа на панели и в оверлей ОС, и там видна длина матча.
- **Простое исправление:** в мосту заменить `navigator.mediaSession.setPositionState` на пустую функцию, пока у `<html>` есть класс `yas-hide-time`. Полностью убрать позицию, которую браузер берёт из самого `<video>`, вероятно, нельзя — это нужно описать в README как ограничение.
- **Статус:** гипотеза.

### C18. Классы скрытия ставятся только после асинхронного чтения storage
- **Файл:** `src/content/content.js:673-689`, `:567-572`.
- **Что не так:** стиль вставляется синхронно, но все правила привязаны к `html.yas-*`, а классы появляются только в `.then` у `readSettings`. Если чтение задержится (старт браузера с десятками вкладок), длительности на карточках успеют отрисоваться.
- **Простое исправление:** в `init` до `refresh()` синхронно добавить `yas-extension-enabled` и `yas-hide-time` (время обязательно). `applySettings` потом приведёт всё к сохранённому состоянию.
- **Статус:** гипотеза (окно обычно несколько мс).

### C19. Результат live-state не сверяется по `requestId`, источник события не проверяется
- **Файл:** `src/content/live-start-controller.js:704-715`.
- **Что не так:** `requestId` отправляется, но при приёме не сверяется. Любой скрипт страницы (реклама, сторонний iframe-скрипт в топ-фрейме) может прислать `{videoId:<текущий>, isLive:false}` и снять щит. В MAIN-мир через мост доступны только действия, которые страница и так может выполнить, поэтому эскалации прав нет.
- **Простое исправление:** принимать результат только с `requestId === nextLiveStateRequestId`.
- **Статус:** подтверждено по коду; практический риск низкий.

### C20. Попап: сообщение «Could not save settings» не исчезает после следующего успешного сохранения
- **Файл:** `popup/popup.js:106-118` (`setStatus` вызывается только при ошибке).
- **Простое исправление:** `setStatus("")` после успешного `writeSettings`.
- **Статус:** подтверждено по коду.

### C21. Mute и unmute идут напрямую через `video.muted`, мимо API плеера
- **Файл:** `src/content/live-start-controller.js:471-502`.
- **Что не так:** внутреннее состояние громкости YouTube (иконка mute, сохранённое `yt-player-volume`) может разойтись с элементом. Если вкладку закрыть или перезагрузить во время щита, исходное `mutedVideoWasMuted` теряется.
- **Простое исправление:** mute и unmute через мост (`player.mute()` / `player.unMute()`, `player.isMuted()` для исходного состояния).
- **Статус:** гипотеза.

## Проверено и находкой не считаю
- Мост MAIN↔isolated: все `detail` — JSON-строки (объекты между мирами не переходят), парсинг в `try`. Ошибка парсинга ведёт к безопасному игнорированию.

- Попап → другие вкладки: `storage.onChanged` в каждой вкладке перечитывает настройки. Legacy-ключи удаляются после записи и игнорируются при чтении.
- Повторная инициализация защищена флагами на `window` изолированного мира.
